# API Overview

The backend API is a FastAPI service that exposes both HTTP endpoints and a websocket endpoint.

This page focuses on the shared rules that apply to the API as a whole. The individual HTTP endpoints are already described in the [Swagger UI](https://virtual-patients-tum.com/api/docs).

## API groups

- Authentication and login
- Session creation and message history (including live API)
- Medical Diagnostics (for the different cases)
- Healthchecks of the System

## Authentication model

Most requests require a signed session cookie named `session`.

- For TUM users, the cookie is set during OIDC login.
- For VHB users, the cookie is derived from the shared-password login flow.
- If `REQUIRE_AUTH=false`, the backend falls back to an anonymous user.

The websocket endpoint uses the same cookie-based session identity as the HTTP API.

## Session model

The backend treats a session as the unit of work for a patient case.

- A session belongs to one case and authenticated user (unless auth is disabled).
- Messages are appended in order and reused as conversation history (also for evaluation).

## Response style

Each response is handled with a ResponseModel of FastAPI and thus always has the same format for answering requests.

Errors are handled via raise HTTPException (with corresponding status_codes)

## [Live feature](/api-features/live_api)

The live feature opens a websocket, forwards microphone audio or user text input to Gemini Live, and streams transcript
and audio events back to the client while tracking the remaining live time for the session.
